# Architecture review

Review the architecture of the path or repo the user names (the current repo if none), with an
optional focus.

Structure, not content: `brain-audit` scores the notes and habits; this asks whether the shape
still fits what the system does now. Uses only shell and reading. **Read-only** until the owner
agrees to a change.
1. **Inventory.** Top-level folders with file counts and sizes (`du`, `find | wc`), entry points
   (README, CLAUDE.md, AGENTS.md, package.json scripts, workflows), generated files and their
   generators, stores (DBs, KV, JSON, APIs) and who reads or writes each, scheduled jobs, deploys.
2. **Draw the data flow**: capture → storage → generated views → readers (people, routines, sites).
   A short arrow list or a Mermaid diagram. Mark every place the same fact is stored twice.
3. **Context cost.** What a fresh Claude session must read to start work: CLAUDE.md size (lines,
   ~tokens = chars/4), always-loaded memory, files the instructions say to read first, and the
   biggest files it's likely to open. Flag anything over ~10k tokens loaded by default.
4. **Judge against these**, each `ok` / `drift` / `problem`, with evidence (paths, counts):
   - **Single source of truth:** each fact has one home; other places point or generate.
   - **Clear boundaries:** each folder or store has one purpose; private data stays fenced.
   - **Generated vs hand-written:** generated files are marked, never hand-edited, regenerated by CI.
   - **Docs match reality:** the folder map and docs name paths that exist, and everything that
     exists is named (`ls` vs the map).
   - **Dead weight:** folders, scripts, workflows or apps unused or untouched in 90+ days (`git log`).
   - **Coupling:** shared code copied between repos, cross-repo reads, one change needing N files.
   - **Failure modes:** what breaks silently (a routine dying, a stale cache, a sync lagging) and
     whether anything would notice.
   - **Scaling:** what gets painful at 2x the notes, apps or users (slow builds, giant indexes).
5. **Recommendations**: max 7, ranked by payoff over effort, each with the problem it fixes, the
   change, the files touched, the risk and an effort estimate. Mark which are safe to do now.
6. **Write it** to `arch-review-<name>-<YYYY-MM-DD>.md` (outside the reviewed repo unless the owner
   wants it inside), with the inventory, diagram, context cost, scorecard and recommendations, plus a
   matching `.html` page in the Next theme (`theme/report.html` with `theme/next.css` pasted into its
   `<style>`; `ok`/`drift`/`problem` as pills).

Reply with the 3 biggest problems (one line each), the default context cost, and the review's path.
